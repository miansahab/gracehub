1. Introduction
1.1 Purpose
GRACE Hub is a custom, unified operations platform for a mid-sized nonprofit organization. It unifies departments on one system, automates workflows, centralizes organizational knowledge, and gives leadership real-time operational visibility. This document specifies the full functional and non-functional requirement set alongside a delivery plan for three-person team delivery.
1.2 Scope
In scope: platform infrastructure (identity, permissions, workflow, notifications, search, AI, audit, storage); the nine departmental modules; integrations with Azure Entra ID, Microsoft 365, QuickBooks, and Bill.com; and organization-wide AI features and universal search.
Out of scope (Phase 4, future): white-label theming, multi-organization tenancy, subscription management, client administration, partner portals, public APIs, and a module marketplace. These are documented for architectural awareness but are not deliverables of this engagement.
1.3 Delivery Model for This Scenario
Three developers work in parallel - two full-stack engineers and one QA specialist - splitting the same workload to compress delivery into a quarter of the calendar time. A short shared foundation sprint precedes parallel module work; QA runs continuously alongside development rather than as a final phase.
Note: The details for the items mentioned below are heavily inclined to change. Depending on client specific requirements, they will be altered. Right now, the processes expected of a suit of this scale are inclued.
2. Architecture Overview
2.1 Logical Architecture
The platform follows a modular, service-oriented architecture: a presentation layer (responsive, mobile-first web application); an application layer (one independently deployable module per department); shared platform services (auth, workflow, notifications, search, documents, AI, audit) consumed by every module rather than duplicated; a data layer (relational system of record, object storage, search index); and an integration layer of queued, retryable connectors.

3. Identity, Access & Security Requirements
ID
| Requirement
SEC-01
| The system must authenticate users exclusively via Azure Entra ID single sign-on (OIDC/SAML). No local passwords.
SEC-02
| User provisioning and deactivation should sync from Entra ID (SCIM or scheduled directory sync); deactivated users must lose access within 15 minutes.
SEC-03
| The system must implement role-based access control with multi-level permissions: platform roles (admin, staff, board, read-only), department scopes, and record-level restrictions.
SEC-04
| Permission checks must be enforced server-side on every API call; UI hiding alone is not sufficient.
SEC-05
| Administrators must be able to manage users, roles, and department scopes through an admin UI without developer involvement.
SEC-06
| The system must write an immutable audit log for all create, update, delete, permission-change, export, and login events.
SEC-07
| Audit logs must be searchable by administrators and retained for a minimum of seven years.
SEC-08
| All data must be encrypted in transit (TLS 1.2+) and at rest.
SEC-09
| The system must support field-level sensitivity flags (e.g., donor wealth data, HR records) that restrict visibility to authorized roles.
SEC-10
| Backups must run at least daily with a documented disaster recovery plan; targets: RPO ≤ 24 hours, RTO ≤ 8 hours.

5. Core Data Model
Twelve shared entities form the system of record, referenced across multiple modules rather than owned by any single one.
Entity
| Description & Key Relationships
Contact
| Person or organization; household grouping, relationship mapping, notes, attachments, communication history. Shared by Advancement, Communications, Events, and Programs.
Gift / Pledge
| Financial contribution linked to a Contact and optionally a Campaign, Event, or Grant. One-time, recurring, pledge, sponsorship, tribute, matching, grant revenue.
Campaign
| Fundraising campaign aggregating gifts, communications, and attribution.
Prospect Plan
| Moves-management record on a Contact: stage, proposal tracking, tasks, assigned officer.
Funder / Grant
| Funder profile plus grant records across the lifecycle, with amount, dates, restrictions, payment schedule, agreements, milestones, and reporting deadlines.
Event
| Event with venue, dates, budget, staff assignments, registrations/tickets, check-in, sponsors, vendors, and financials.
Program
| Program/cohort/initiative with participants, volunteers, and impact metrics.
Financial Record
| Purchase orders, invoices, payments, and budget lines synchronized with QuickBooks and Bill.com.
Task / Project
| Assignable task with due date, project grouping, and workflow linkage; surfaces in Task Center.
Board Record
| Board meetings, agendas, packets, minutes, governance documents, members, and committees.
Knowledge Asset
| Policies, SOPs, templates, boilerplate text, forms, and training content with tags and permissions.
Communication
| Logged email, call, meeting, or campaign touch tied to Contacts and Campaigns, with engagement metrics.

7. Integration Requirements
System
| Direction & Data Notes
Azure Entra ID
| Inbound: authentication (SSO), user provisioning, group-to-role mapping. OIDC preferred; deactivation propagates within 15 minutes.
Microsoft 365
| Bi-directional: calendar events, email send/log, document viewing/editing (SharePoint/OneDrive), meeting artifacts. Via Graph API, respecting M365 permissions.
QuickBooks
| Bi-directional: chart of accounts, transactions, budgets in; invoices/bills and class/department coding out. Scheduled sync hourly; reconciliation report for sync errors.
Bill.com
| Bi-directional: vendors, bills, approval status, payment status. Approval state must reconcile with the platform&apos;s own workflow to avoid dual approval conflicts.
ID
| Requirement
INT-01
| All integrations must be queued and retryable, with an admin-visible sync log, error queue, and alerting on repeated failures.
INT-02
| A single source of truth must be designated per data domain (e.g., QuickBooks for the general ledger, GRACE Hub for donors/grants).
INT-03
| Integration credentials must be stored in a secrets manager, never in code or configuration files.
